## กับดักที่เสียเวลาไปกับมัน (บันทึกไว้กันพลาดซ้ำ)

1. **`--image-max-tokens` ต่ำกว่า 1024 = โมเดลพัง** llama.cpp เตือนเองตอนโหลด:
   > `Qwen-VL models require at minimum 1024 image tokens to function correctly`
   > `try adding --image-min-tokens 1024` — [ggml-org/llama.cpp#16842](https://github.com/ggml-org/llama.cpp/issues/16842)

   ที่ 256 tokens โมเดลพ่นพิกัด `<|box_start|>(10,10),(992,984)<|box_end|>` แทนข้อความ
   **ผลทดสอบรอบแรกทั้งหมดจึงใช้ไม่ได้** — อ่าน warning ตอนโหลดโมเดลก่อนเสมอ
2. **`.webp` ต้องแปลงเป็น png ก่อน** — llama.cpp คืนผลว่างใน 2 วินาที (LINE ส่ง webp ได้ ต้องเผื่อ)
3. **mmproj Q8_0 (677MB) ไม่ใช่ f16 (1270MB)** — ต่างกัน 600MB คือเส้นแบ่งว่าจะลง VPS ได้ไหม
4. **`-c 4096` → `-c 2048` ลดแรมได้ ~850MB** (3,393 → 2,539 MB) แรมส่วนใหญ่คือ context/compute buffer
   ไม่ใช่น้ำหนักโมเดล
5. **vision encoder คือคอขวด ไม่ใช่ prefill** — 29 จาก 41 วินาที (71%) เป็น `mtmd batch encoding`

## ที่ยังไม่ได้ลอง (ถ้าจะดันต่อ)

- `--image-min-tokens 1024` + ความละเอียดสูงกว่านี้ → คุณภาพน่าจะดีขึ้น แต่ **แรม/เวลาเต็มเพดานแล้ว**
- Qwen2.5-VL-3B — OCR ดีกว่า แต่ใหญ่กว่า ใส่ 2.9GB ไม่ลงแน่
- **PaddleOCR / Tesseract บน CPU** (~2–5 วิ/รูป, แรมไม่กี่ร้อย MB) → ป้อนเข้า parser เดิม
  ยังไม่ได้วัด — เป็นทางเดียวที่เหลือถ้าอยากให้ VPS ทำงานเองจริง ๆ

## หลังแก้ parser 3 จุด: **15/15** (เดิม 9/15)

| รูป | ก่อนแก้ | หลังแก้ |
|---|---|---|
| `slip.png` | 5/6 | **6/6** ✅ |
| `สลิปโอนเงิน.webp` (K+ จริง) | 4/6 | **6/6** ✅ |

แก้ที่ `slip-ocr-th/` (self-test เดิมผ่านครบทุกไฟล์ ไม่มี regression):

1. **`slip_parser._DATE_TH`** — OCR ตกจุดบ่อย (`23 กค. 2569`) แต่ regex ต้องการ `ก.ค.` เป๊ะ
   → แต่ละจุดกลายเป็น `\.?` + lookup ผ่าน `_TH_MONTH_NODOT`
2. **`slip_parser._find_parties_by_layout()`** (ใหม่) — สลิป K+ ไม่มีป้าย `จาก:`/`ไปยัง:` ใช้ลูกศร ↓
   → หาบรรทัดเลขบัญชีแล้วถอยขึ้นไปหาบรรทัดที่ดูเป็นชื่อ บล็อกแรก=ผู้โอน บล็อกสอง=ผู้รับ
   ทำงานเฉพาะตอนหาป้ายไม่เจอทั้งคู่ + เติม warning ว่าเป็นการเดา
   **ไล่ด้วย index ไม่ใช่ค่าสตริง** — สลิปโอนเข้าบัญชีตัวเองมีชื่อซ้ำกันสองบล็อก
3. **`payslip_parser._pairs_crossline()`** (ใหม่) — OCR แบบกล่องต่อกล่องคืนป้าย/ค่าคนละบรรทัด
   แต่ `_pairs()` ดูเฉพาะบรรทัดเดียวกัน → จับคู่ข้ามบรรทัดแบบ LIFO (ป้ายใกล้สุดก่อน)
   ต้องใช้ `_MONEY_ONLY_LINE` ที่เข้มกว่า `_MONEY_RE` เพราะตัวเดิมโลภ จับ `2565` จากวันที่
   และ `8888` จากเลขบัญชี → จับคู่มั่วทั้งตาราง

**บั๊กที่มีอยู่เดิม เจอระหว่างทาง (ข้อ 4):**

4. **`payslip_parser._labeled_val()`** — `_labeled` ใช้ `re.S` ทำให้ gap `.{0,25}?` ข้าม newline
   **และข้ามป้ายอื่น** ไปหยิบเลขของคอลัมน์อื่นได้:
   ```
   รับสุทธิ \n รมรายได้ \n 51,500.00   ← เลขของ "รวมรายได้" ไม่ใช่ "เงินรับสุทธิ"
   ```
   fuzzy ชั้น 2 ได้ถูกอยู่แล้ว แต่ชั้น 1 ชนะเพราะ fuzzy เติมเฉพาะฟิลด์ที่ยังว่าง
   → `search()` → `finditer()` + ข้ามคู่ที่ gap มีทั้ง newline และตัวอักษร
   (gap เป็น newline เปล่ายังรับ = ป้ายคนละบรรทัดกับค่า; `" THB "` ในบรรทัดเดียวกันยังรับ)

   ⚠️ **ยังไม่ได้รัน `eval_payslip.py`** (ชุดสังเคราะห์ที่เคยได้ 27/27) เพราะต้องสตาร์ท
   `serve.py` + ใช้ GPU — การแก้ข้อ 4 แตะ path ที่ eval ตัวนั้นวัดตรง ๆ **ควรรันยืนยันก่อนถือว่าจบ**

## เพดานย้ายจาก OCR ไปอยู่ที่ parser แล้ว

**ค่าที่ต้องการอยู่ในข้อความ OCR ครบ 15/15 ตัว** แต่ parser ดึงออกได้ 9 — ตรงข้ามกับสถานการณ์
ของ Unlimited-OCR ที่ `slip-ocr-th/ROADMAP.md` เขียนไว้ว่า *"เพดานจริงอยู่ที่ OCR"*

ผลอ่านสลิป K+ จริง — **ถูกทุกบรรทัด**:
```
โอนเงินสำเร็จ / K+ / 26 ม.ค.65 05:10 น.
นายกสิกร รักไทย / ธ.กสิกรไทย / xxx-x-x8888-x
เลขที่รายการ: 123456789012345678
จำนวน: 888.00 บาท / ค่าธรรมเนียม: 0.00 บาท
```

ที่ parser ยังดึงไม่ได้ **ไม่ใช่ความผิด OCR**:

| ปัญหา | สาเหตุจริง | แก้ที่ไหน |
|---|---|---|
| `date` ของ `slip.png` | OCR ได้ `23 กค. 2569` (ตกจุด) แต่ `_TH_MONTH` ต้องการ `ก.ค.` เป๊ะ | `slip_parser.py` — normalize จุดก่อน lookup |
| `from`/`to` ของสลิป K+ | **สลิปใบนี้ไม่มีป้าย "จาก:"/"ไปยัง:"** ใช้ลูกศร ↓ แทน — `_FROM`/`_TO` จับไม่ได้แน่นอน | ต้องอ่านจาก layout (เฉลยใน `truth.json` ตั้งไว้ไม่แฟร์) |
| ใบเงินเดือน 0/3 | ป้ายเพี้ยนเล็กน้อย (`รวมรายการนัก`, `เงันรับสุทธิ`, `รมรายได้`) fuzzy-match ยังไม่กู้ | `payslip_parser.py` — จูน threshold |

## กับดัก PaddleOCR (เสียเวลาไปกับสองอันนี้)

1. **`enable_mkldnn=False` จำเป็น และต้องส่งเป็น argument เท่านั้น**
   ไม่ปิด → `NotImplementedError: ConvertPirAttribute2RuntimeAttribute ... onednn_instruction.cc:116`
   env `FLAGS_use_mkldnn=0` / `FLAGS_enable_pir_api=0` **ไม่มีผล** (ลองแล้วทั้งคู่)
2. **พอ override `text_detection_model_name` ต้องระบุ `text_recognition_model_name="th_PP-OCRv5_mobile_rec"` ด้วย**
   ไม่งั้นมันเลิก auto-เลือกจาก `lang="th"` แล้วถอยไปใช้ rec ตัว latin → ไทยออกมาเป็น `τəuιūuιν`
   **แต่ตัวเลขยังถูกหมด** → ถ้าดูแค่ยอดเงินจะไม่รู้เลยว่าตั้งค่าพลาด

ตัดออกได้เพื่อลดแรม: `use_doc_orientation_classify` / `use_doc_unwarping` / `use_textline_orientation`
(สลิปมือถือตั้งตรงอยู่แล้ว + `preprocess.py` ทำ EXIF auto-orient ให้) และใช้ `mobile_det` แทน `server_det`
→ ลด peak RSS จาก **3,892 → 715 MB**

## ข้อควรระวังในการอ่านตัวเลขพวกนี้

- **ทั้ง SROIE และ thai-ocr-eval ไม่ใช่งานจริงของโปรเจกต์** — SROIE เป็นใบเสร็จร้านค้าต่างประเทศ
  ส่วน thai-ocr-eval เป็น **crop คำ/บรรทัดเดี่ยว** ไม่ใช่เอกสารทั้งใบ
  17% ของ GPU บนชุด crop ไม่ได้แปลว่าอ่านสลิปได้ 17% — บนสลิปเต็มใบมันอ่าน 888.00 + ref ถูก
- **ชุดที่ตัดสินจริงคือสลิปไทย 332 ใบ** สองชุดนี้เป็นข้อมูลประกอบว่า engine ไหนทนกับเอกสารนอกโดเมนได้ดีกว่า
- `parse_receipt` แย่ลงเมื่อใช้กับ PaddleOCR (62%→54%) เพราะตรรกะเลือกยอดรวมถูกจูนมากับรูปแบบ
  ข้อความของ Unlimited-OCR — ถ้าจะย้าย engine ถาวร ควรจูน `parse_receipt` ใหม่ด้วย
- **ยืนยัน regression:** ตัวเลข SROIE ฝั่ง GPU (62%) ตรงกับที่ `ROADMAP.md` บันทึกไว้ก่อนแก้ parser
  → การแก้ parser 7 จุดไม่ทำของเดิมพัง (เป็นการตรวจชุดที่ 3 ต่อจาก self-test และ `eval_payslip` 27/27)

# คำแนะนำ (อัปเดตหลังวัด PaddleOCR)

**เปลี่ยนจากข้อสรุปก่อนหน้า** — ตอนวัดได้แค่ Qwen2-VL ผมสรุปว่า VPS เป็นสมองไม่ได้
พอวัด PaddleOCR แล้ว **VPS ทำเองได้จริงสำหรับ phase 1 (สลิปโอน)**: 715 MB + 5.6 วิ/รูป
อ่านสลิป K+ จริงได้ครบ และเหลือแรมให้ Node bot อีก ~2.2 GB

| ทางเลือก | เมื่อไรควรใช้ |
|---|---|
| **VPS + PaddleOCR ทั้งหมด** | phase 1 สลิปโอน — ไม่ต้องเปิดคอมบ้าน ตอบใน ~6 วิ (reply token ไม่ตาย) |
| VPS หน้าบ้าน + GPU บ้านเป็นสมอง | เมื่อต้องการใบเงินเดือน/เอกสารยาก ที่ Unlimited-OCR ยังเหนือกว่า |
| ทั้งคู่ (fallback chain) | `/parse` ลอง GPU บ้านก่อน ตายแล้วค่อยตก PaddleOCR บน VPS |

โค้ดใน `src/` รองรับทุกแบบอยู่แล้ว — เปลี่ยนแค่ `OCR_ENDPOINT` ใน `.env`
และเมื่อ backend ล่ม `ocrClient.js` โยน `OcrUnavailableError` → บอทตอบผู้ใช้ว่าระบบไม่พร้อม แทนที่จะเงียบ
